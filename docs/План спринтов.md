с исполнителем и привязана к **Milestone** своего спринта; номер Issue указан в заголовке задачи.

## 2. Правила работы с репозиторием

1. В ветке `main` изначально только `README.md` с названием проекта; всё остальное
   попадает туда **только через Pull request**.
2. На каждую задачу — свой Issue с привязкой к Milestone и исполнителем.
3. На каждый Issue — отдельная ветка от `main`. Именование:
   - `docs/<краткое-имя>` — документация и требования;
   - `feature/<краткое-имя>` — новая функциональность;
   - `fix/<краткое-имя>` — исправление.
4. Pull request ссылается на Issue строкой `Closes #N`, чтобы задача закрывалась при слиянии.
5. **Merge только после Review с Approve преподавателя.**
   - В спринте 1 ревью запрашивается у **всех участников команды и преподавателя**.
   - В спринтах 2–4 достаточно ревью **одного участника команды и преподавателя**.
6. Никаких прямых коммитов в `main` и никакого `git push --force` в общие ветки.
7. Секреты (`.env`, токены) в репозиторий не попадают — только шаблон `.env.example`.

### Milestones

| Milestone | Спринт | Содержание |
|---|---|---|
| Постановка задачи | 1 | README, ТЗ, базовый проект и инструкция по запуску |
| Ядро системы | 2 | Вход по ролям, ученики и родители, расписание, занятия, кабинеты |
| Финансы и уведомления | 3 | Платежи и баланс, страница «Финансы», уведомления на сайте |
| Telegram, теория и релиз | 4 | Telegram-бот, раздел «Теория», прод-сборка и сдача |

### Определение готовности (Definition of Done)

Задача считается выполненной, когда: код собирается (import-смоук для backend,
`npm run build` для фронтенда), сценарий из критериев приёмки воспроизведён вручную
на стенде, документация обновлена, PR получил Approve и влит в `main`, Issue закрыт.

- Критерии приёмки: на тестовом занятии напоминания приходят в срок и ровно один раз;
  перезапуск worker'а дублей не создаёт.

- Состав работ: карточка привязки Telegram в профиле (код, срок действия, статус,
  отвязка); проверка и доработка вёрстки на экранах от 360 px; единообразие
  состояний загрузки, пустых списков и ошибок; прод-сборка фронтенда без предупреждений.
- Критерии приёмки: все страницы пригодны к работе на телефоне; пользователь
  привязывает Telegram по инструкции на экране.

### Максим (backend)

**Issue #20 — Telegram-бот: привязка кодом и доставка уведомлений**
- **Ветка:** `feature/telegram-bot`
- Состав работ: модель и миграция `telegram_links`; клиент Telegram Bot API; бот
  в worker'е на long polling с приёмом шестизначного кода; доставщик накопившихся
  уведомлений; снятие привязки при блокировке бота; API привязки и отвязки;
  корректная работа при пустом токене.
- Критерии приёмки: пользователь привязывает аккаунт кодом и получает следующее
  уведомление в Telegram; при пустом токене сайт работает, а бот не стартует.

**Issue #21 — API раздела «Теория»**
- **Ветка:** `feature/theory-api`
- Состав работ: модели и миграция `topics`, `materials`, `material_files`; чистая логика
  дерева (сборка, фильтрация по видимости, ограничение глубины) и смоук-скрипт;
  сервис и роутер; файлы материалов с проверкой публикации; ручной порядок;
  каскадное удаление темы с очисткой файлов; поиск; сквозной смоук-прогон API.
- Критерии приёмки: черновик недоступен ученику и отдаёт «не найдено»; удаление темы
  уносит поддерево и файлы; поиск находит тему и материал по подстроке.

**Issue #22 — Прод-сборка и деплой**
- **Ветка:** `feature/release-deploy`
- Состав работ: автоматическое применение миграций при старте backend; настройка
  внешнего порта и `APP_ORIGIN`; тома для загрузок и данных БД; проверка полного цикла
  на чистом клоне; финальное обновление инструкции по запуску.
- Критерии приёмки: `docker compose up -d --build` на чистой машине даёт рабочий стенд
  со всеми подсистемами; повторный запуск не теряет данные.
