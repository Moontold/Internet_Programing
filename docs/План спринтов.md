# План спринтов и распределение задач

Документ фиксирует роли в команде, правила работы с репозиторием и состав задач
по четырём спринтам. Каждая задача из этого документа заводится в GitHub как **Issue**
и привязывается к **Milestone** своего спринта.

## 2. Правила работы с репозиторием

1. В ветке `main` изначально только `README.md` с названием проекта; всё остальное
   попадает туда **только через Pull request**.
2. На каждую задачу — свой Issue с привязкой к Milestone и исполнителем.
3. На каждый Issue — отдельная ветка от `main`. Именование:
   - `docs/<краткое-имя>` — документация и аналитика;
   - `feature/<краткое-имя>` — новая функциональность;
   - `fix/<краткое-имя>` — исправление.
4. Pull request ссылается на Issue строкой `Closes #N`, чтобы задача закрывалась сама.
5. **Merge только после Review с Approve преподавателя.**
   - В спринте 1 ревью запрашивается у **всех участников команды и преподавателя**.
   - В спринтах 2–4 достаточно ревью **одного участника команды и преподавателя**.
6. Никаких прямых коммитов в `main` и никакого `git push --force` в общие ветки.
7. Секреты (`.env`, токены) в репозиторий не попадают — только `.env.example`.
8. Ветка `project/full` — архивная полная версия проекта, в `main` не вливается;
   она служит эталоном, из которого собираются спринты.

### Milestones

| Milestone | Спринт | Содержание |
|---|---|---|
| Постановка задачи | 1 | README, ТЗ, базовый проект |
| Ядро системы | 2 | Роли, ученики и родители, расписание, занятия, кабинеты |
| Финансы и уведомления | 3 | Платежи и баланс, страница «Финансы», уведомления на сайте |
| Telegram, теория и релиз | 4 | Telegram-бот, раздел «Теория», прод-сборка и сдача |

### Определение готовности (Definition of Done)

Задача считается выполненной, когда: код собирается (`py_compile` / import-смоук для
backend, `tsc -b && vite build` для фронтенда), сценарий из критериев приёмки воспроизведён
вручную на стенде, документация обновлена, PR получил Approve и влит в `main`, Issue закрыт.
