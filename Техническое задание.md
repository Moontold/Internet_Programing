# Техническое задание

**Проект:** «Сайт репетитора» — веб-приложение для ведения частной репетиторской практики.
**Заказчик:** частный преподаватель (репетитор), ведущий индивидуальные и групповые занятия.
**Команда:** продукт-менеджер, бизнес-аналитик, разработчик (состав — в [README.md](./README.md)).
**Документ версии:** 1.0, спринт 1 «Постановка задачи».

---

## 1. Назначение и цели

### 1.1 Проблема

Репетитор ведёт расписание в календаре, домашние задания — в мессенджере, оплаты — в
таблице. Данные разъезжаются: родитель не знает, сколько должен, ученик теряет домашку,
репетитор вручную считает заработок и вручную напоминает о занятиях.

### 1.2 Цель проекта

Одно веб-приложение, в котором репетитор ведёт расписание, занятия и оплаты, а родители
и ученики видят свою часть этих данных и вовремя получают уведомления.

### 1.3 Измеримые результаты

| Что | Как проверяем |
|---|---|
| Расписание ведётся в приложении | Серия занятий создаётся один раз, занятия на 12 недель вперёд появляются сами |
| Домашка не теряется | Домашнее задание с файлами привязано к занятию и доступно ученику и родителю |
| Оплаты прозрачны | Баланс родителя считается автоматически, «оплачено/не оплачено» видно на занятии |
| Никто не забывает о занятии | Уведомление приходит на сайт и в Telegram за сутки (ученику и родителю) и за 30 минут (репетитору) |
| Развёртывание воспроизводимо | `docker compose up -d --build` поднимает систему с нуля на чистой машине |

### 1.4 Границы проекта (что не делаем)

Онлайн-оплата и эквайринг, видеосвязь внутри сайта, мобильные приложения, мультиарендность
(несколько репетиторов в одной установке), автоматическая проверка домашних заданий.

## 2. Тип проекта и общая архитектура

**Тип:** веб-приложение. Одностраничное клиентское приложение (SPA) + REST API.

```
Браузер (React SPA)
        │  HTTPS, cookie-сессия
        ▼
nginx ──/api/──► FastAPI (backend) ──► PostgreSQL 16
  │                                        ▲
  └── статика SPA                          │
                              worker ──────┘
                   (планировщик занятий, рассылка уведомлений, Telegram-бот)
```

- Наружу открыт единственный порт — `nginx` фронтенда; backend и БД доступны только внутри
  сети docker compose.
- Backend разделён на слои `routers → services → repositories`; расчёты (расписание,
  баланс, тексты уведомлений, дерево тем) вынесены в чистые функции `core/` без обращений
  к БД и сети.
- `worker` — отдельный контейнер на том же образе: порождает занятия из серий, закрывает
  прошедшие занятия, создаёт и доставляет уведомления, принимает коды привязки Telegram.

## 3. Роли пользователей и права

| Роль | Кто это | Что доступно |
|---|---|---|
| **Репетитор** | Владелец установки, единственный аккаунт с этой ролью | Всё: расписание, ученики, родители, занятия, домашки и оценки, финансы, теория, уведомления |
| **Родитель** | Плательщик, у него один или несколько детей | Свои дети, их занятия и домашки, свой баланс и долг, теория (опубликованное), уведомления |
| **Ученик** | Ребёнок родителя | Своё расписание, свои занятия, домашки и оценки, теория (опубликованное), уведомления. Финансы недоступны |

Учётные записи родителей и учеников создаёт репетитор; пароль показывается один раз при
создании и может быть сброшен из карточки. Регистрации снаружи нет.

## 4. Функциональные требования

Требования сгруппированы по подсистемам; в скобках — спринт, в котором требование
реализуется (см. [план спринтов](./docs/План%20спринтов.md)).

### 4.1 Аутентификация и доступ (спринт 2)

- ФТ-1. Вход по логину и паролю; пароль хранится хешем (argon2), сессия — в httpOnly-cookie.
- ФТ-2. Учётка репетитора создаётся при первом старте из переменных окружения.
- ФТ-3. Каждый запрос к API проверяет роль; чужие данные отдают 403, несуществующие — 404.
- ФТ-4. Защита от перебора: неудачные попытки входа фиксируются и ограничиваются.
- ФТ-5. Защита от CSRF: запросы, меняющие данные, принимаются только с разрешённого Origin.

### 4.2 Ученики и родители (спринт 2)

- ФТ-6. Репетитор создаёт, редактирует и деактивирует карточки родителей и учеников.
- ФТ-7. Ученик всегда привязан к одному родителю; у родителя может быть несколько детей.
- ФТ-8. В карточке ученика хранятся класс, формат занятий (онлайн/офлайн) и ставка за занятие.
- ФТ-9. Репетитор может сбросить пароль ученика или родителя.

### 4.3 Расписание и занятия (спринт 2)

- ФТ-10. Серия занятий задаётся правилом «каждые N недель в такое-то время», с датой
  окончания или бессрочно; в серии один или несколько учеников.
- ФТ-11. `worker` порождает из серий реальные занятия на горизонт 12 недель вперёд и
  переводит закончившиеся занятия в статус «проведено».
- ФТ-12. Правка серийного занятия даёт выбор области: «только это», «это и последующие»,
  «все занятия».
- ФТ-13. Занятие можно перенести, отменить и удалить; отменённое не списывается со счёта.
- ФТ-14. Календарь репетитора показывает занятия по неделям и дням с фильтрами.
- ФТ-15. Карточка занятия содержит тему, формат, домашнее задание с файлами, а по каждому
  участнику — статус выполнения домашки и оценку.
- ФТ-16. Кабинет родителя: список детей и их занятий. Кабинет ученика: своё расписание,
  домашки и оценки.

### 4.4 Финансы (спринт 3)

- ФТ-17. Ставка копируется из карточки ученика в занятие при порождении и может быть
  изменена в конкретном занятии.
- ФТ-18. Счёт ведётся на родителя: проведённые занятия его детей списываются, отменённые нет.
- ФТ-19. Репетитор вносит платежи (сумма с любым знаком кроме нуля, дата, комментарий),
  платежи можно править и удалять.
- ФТ-20. Баланс и признак «оплачено» не хранятся, а вычисляются: платежи закрывают
  проведённые занятия от самого раннего; частично покрытое занятие считается неоплаченным.
- ФТ-21. Страница «Финансы»: долги и предоплаты по родителям, заработок по месяцам
  (наработано по проведённым занятиям и получено по платежам).
- ФТ-22. Родитель видит только свой баланс и плашки «не оплачено»; ученик финансов не видит.

### 4.5 Уведомления и Telegram (спринты 3 и 4)

- ФТ-23. Уведомление сначала становится записью в БД — единый источник правды для сайта и
  для Telegram.
- ФТ-24. На сайте уведомления показывает колокольчик в шапке: счётчик непрочитанных,
  последние 20 в выпадающем списке, открытие помечает их прочитанными, клик ведёт на
  занятие или на финансы.
- ФТ-25. События и адресаты:

  | Событие | Кому |
  |---|---|
  | за сутки до занятия | ученик и родитель |
  | за полчаса до занятия | репетитор |
  | сохранена домашка к проведённому занятию | ученик и родитель |
  | то же, если у родителя долг | родителю дополнительно напоминание об оплате |
  | занятие отменено или перенесено | ученик и родитель |
  | правка серии «это и последующие» / «все» | ученик и родитель, одним сообщением на серию |
  | через час после занятия нет домашки | репетитор |
  | кнопка «Напомнить об оплате» | родителю |

- ФТ-26. Повторные уведомления гасятся ключом дедупликации; напоминание об оплате и
  уведомление о переносе намеренно повторяемы.
- ФТ-27. Уведомления только о будущих занятиях: отмена задним числом и удаление молчат.
- ФТ-28. Привязка Telegram: пользователь получает в профиле шестизначный код (живёт 15 минут)
  и отправляет его боту; отвязка — там же. Других команд у бота нет.
- ФТ-29. Пустой токен бота — рабочий режим: бот и доставщик не стартуют, уведомления
  остаются на сайте. Если пользователь заблокировал бота, привязка снимается автоматически.

### 4.6 Теория (спринт 4)

- ФТ-30. Дерево тем произвольной глубины (до шести уровней) и материалы внутри тем.
- ФТ-31. Материал — название, текст в Markdown (GFM: таблицы, списки, ссылки) и файлы;
  сырой HTML не исполняется.
- ФТ-32. Материал имеет состояние «черновик» / «опубликован». Ученики и родители видят
  только опубликованное и только те темы, где оно есть; пустые ветки скрываются.
- ФТ-33. Черновик для не-репетитора отдаёт «не найдено», а не «нет доступа».
- ФТ-34. Порядок тем и материалов ручной (кнопки «выше» / «ниже»); удаление темы
  каскадное с подтверждением.
- ФТ-35. Поиск по названиям тем и материалов от двух символов, без учёта регистра.

## 5. Нефункциональные требования

- НФТ-1. **Развёртывание.** Полный стенд поднимается `docker compose up -d --build` из
  чистого клона; миграции БД применяются автоматически при старте backend.
- НФТ-2. **Конфигурация.** Все настройки и секреты — в `.env` (шаблон `.env.example`),
  в коде секретов нет, `.env` не коммитится.
- НФТ-3. **Безопасность.** Пароли — argon2; сессия в httpOnly-cookie, `Secure` при HTTPS;
  проверка Origin для изменяющих запросов; наружу открыт только порт фронтенда.
- НФТ-4. **Данные.** Время в БД хранится в UTC (`TIMESTAMPTZ`), отображается в часовом
  поясе установки (по умолчанию `Europe/Moscow`). Деньги — целые рубли.
- НФТ-5. **Единый формат ответов API.** Все ответы — конверт `{error, message, payload}`;
  бизнес-ошибка возвращается с текстом на русском языке.
- НФТ-6. **Надёжность.** Сбой отправки уведомления не ломает основную операцию; повторный
  проход планировщика не создаёт дубликатов.
- НФТ-7. **Язык интерфейса.** Русский — подписи, ошибки, тексты уведомлений.
- НФТ-8. **Совместимость.** Актуальные версии Chrome, Firefox, Safari, Edge; вёрстка
  работоспособна на экране от 360 px.
- НФТ-9. **Файлы.** Домашки и материалы хранятся в отдельном томе; размер загрузки
  ограничен настройкой (по умолчанию 50 МБ).
- НФТ-10. **Хранение уведомлений.** Записи старше заданного срока (по умолчанию 90 дней)
  удаляются автоматически.

## 6. Модель данных (основные сущности)

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Учётные записи всех ролей | `login`, `password_hash`, `role`, `full_name`, `is_active` |
| `sessions`, `login_attempts` | Сессии и контроль перебора пароля | `token_hash`, `expires_at`; `login`, `success` |
| `parents` | Родитель-плательщик | ссылка на `users`, контакты |
| `students` | Ученик | `parent_id`, `grade`, `format`, `price_per_lesson`, `is_active` |
| `lesson_series` + `series_students` | Правило повторения и состав группы | `first_start`, `duration_minutes`, `interval_weeks`, `until` |
| `lessons` + `lesson_students` | Конкретные занятия и участие в них | `scheduled_start`, `status`, `topic`, `homework_text`; `price`, `homework_status`, `homework_grade` |
| `files` + `lesson_files`, `material_files` | Файлы домашек и материалов | имя, размер, тип, путь в томе |
| `payments` | Платежи родителей | `parent_id`, `amount`, `paid_on`, `comment` |
| `notifications` | Уведомления (источник правды) | получатель, вид, текст, `dedupe_key`, прочитано, доставлено |
| `telegram_links` | Привязка аккаунта к Telegram | код, состояние, `chat_id` |
| `topics`, `materials` | Дерево теории и материалы | родитель, порядок, заголовок, Markdown, признак публикации |

Баланс, долг и признак «оплачено» в БД **не хранятся** — вычисляются из проведённых
занятий и платежей.

## 8. Верификация

Автоматических юнит-тестов в проекте нет; корректность подтверждается:

1. импорт-смоуком всех модулей backend (`scripts/smoke_import.py`);
2. смоук-скриптами чистой логики: расписание, финансы, уведомления, дерево теории;
3. сквозными смоук-прогонами API на поднятом backend (уведомления, теория);
4. сборкой фронтенда `tsc -b && vite build` (типы + бандл);
5. ручным прогоном пользовательских сценариев на стенде `docker compose` — приёмка задачи
   продукт-менеджером по критериям из Issue.

## 10. Критерии приёмки проекта

Проект считается сданным, когда:

1. стенд поднимается из чистого клона по инструкции и доступен в браузере;
2. все три роли работают в своих правах: репетитор ведёт расписание и финансы, родитель
   видит детей и баланс, ученик — расписание и домашки;
3. занятия порождаются из серий автоматически, правка серии поддерживает три области;
4. баланс и признак «оплачено» считаются по описанному алгоритму;
5. уведомления приходят на сайт, а при заданном токене — в Telegram, без дублей;
6. раздел «Теория» доступен по ролям с учётом черновиков;
7. каждая задача закрыта через Issue → ветка → Pull request → code review → merge;
8. README и ТЗ актуальны на момент сдачи.
